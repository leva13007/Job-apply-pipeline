# Job Search

This is a personal, non-code project (see the project's `CLAUDE.md`). State lives in three
places, always read live, never cached into this file:

- `tracker/Job_Search_Tracker.xlsx` — sheets `Job Tracker`, `Search Criteria`, `My Profile`,
  `Recruitment Agencies`.
- `interviews/<company_slug>/` — per-company README + round folders, created only once a
  company reaches an actual response/interview stage.
- This project's top-level `README.md` — "where I left off" / "next step" / running
  applications log.

## Non-negotiable rules

These apply across every mode below, not just `search`.

- **Confidentiality from current employer (The AA):** never take an action that increases
  visibility of the search — no switching LinkedIn "Open to Work" to public, no posts,
  comments, or likes that would surface it. Keep it as low-key as the existing
  "recruiters only" setting.
- **Per-run application quota:** authorization to submit is granted once, up front, by
  Oleh's own request — not by a slow-escalating persistent counter. When Oleh asks to run a
  job search, his request states (or is asked for once, if missing) the source(s) and the
  number of applications to submit this run — e.g. "apply to 5 roles from LinkedIn." That
  count is the ceiling for the run. Within it, `search` goes through fitting, deduped
  postings and submits Easy Apply without asking again per individual Submit — the upfront
  quota *is* the confirmation. Exceptions that still stop and ask mid-run:
    - a posting fails a stated `Search Criteria` constraint (format/location/salary) — flag it
      before spending quota on it, same as any other fit judgment call, not a permission gate;
    - the tailored CV content itself, before it's used (see `tailor` below) — still gets a
      sanity-check from Oleh;
    - `lead` and `update` writes still get a quick confirmation before writing, since those
      aren't covered by a `search` quota.
      If fitting postings run out before the quota is reached, stop and report — don't lower the
      bar just to hit the number.
- **`My Profile` sheet (EEO / sensitive data):** DOB, right-to-work/visa status, gender
  identity, sexual orientation, ethnicity, religion, disability status, current salary — use
  these values only to literally fill an application form field. Never restate, quote, or log
  them anywhere else, including chat summaries or the tracker's Notes column.
  Never read, print, or commit `.env` files, and never touch anything under `the_life/`.
- **Transcripts / recordings:** never summarize, quote, or restate `interviews/**`
  transcript, `.wav`, or reflection content outside this project's own files.
- **Dedup:** before applying, check the entire `Job Tracker` sheet (not just recent rows) —
  match by company + title, or by link. A match is skipped silently and automatically — list
  it in the end-of-run summary, don't stop to ask about it.

## Reference data

- Master resume (tailoring source): `cv/base/resume_master.md` — comprehensive, includes an
  extended bullet pool not yet folded into the canonical CV. Never send this as-is; `tailor`
  selects/trims/reorders from it per posting.
- Submitted CVs: `cv/tailored/<company_slug>/Oleh_Levchenko_CV.pdf` — always holds the exact
  file that was attached for that application, whether generated by `tailor` or snapshotted
  from the canonical PDF at `search` time (see `search` step 5). This is the path logged in
  the tracker's `CV Used` column. Local-only (git-ignored except the folder's own
  `README.md`).
- Preferences / constraints / search parameters: `Search Criteria` sheet.
- Application-form autofill values: `My Profile` sheet.

Read these sheets live each run rather than duplicating numbers here — the xlsx is the one
source of truth.

## Dispatch on `$ARGUMENTS`

| argument | purpose |
|---|---|
| `search` (default, no argument) | Go through LinkedIn listings and apply to ones that fit |
| `lead <company>` | Log an inbound recruiter message/email |
| `tailor <company>` | Generate a per-posting tailored CV |
| `update <company>` | Record a response/interview outcome and move state forward |

### `search`

1. Determine this run's quota: source(s) + application count. Use what Oleh already stated
   in his request; if he didn't give a count, ask once before starting (not per posting).
   Open LinkedIn → Jobs. Filters are already configured on the account — don't reconfigure
   them each session.
2. Go through the listed positions in order. For each one, check fit against the
   `Search Criteria` and `My Profile` sheets (role level, stack, location/format, salary if
   listed).
3. Skip positions already present in `Job Tracker` (see Dedup above) — silently, no need to
   ask.
4. If it fits, run `tailor <company>` (see below) to generate a posting-specific CV before
   applying — this is the default, not an optional extra step.
5. Apply — via LinkedIn Easy Apply, or by following through to an external site if the
   posting requires it:
    - Attach the tailored PDF from step 4 (`cv/tailored/<company_slug>/Oleh_Levchenko_CV.pdf`)
      once Oleh has exported it. If it isn't exported yet, ask Oleh to export it now, or fall
      back to the canonical `cv/v2/Oleh_Levchenko_CV.pdf` if Oleh says to skip tailoring for
      this one — if you fall back, `cp` the canonical PDF to
      `cv/tailored/<company_slug>/Oleh_Levchenko_CV.pdf` first, so a fixed snapshot of exactly
      what was sent exists there too, independent of later edits to `cv/v2`.
    - Use the cover letter template below when a cover-letter field exists.
    - Use `My Profile` values to answer form questions (contact info, right-to-work, salary
      expectation, notice period, EEO/demographic questions if forced).
    - Submit directly — no per-application confirmation needed while inside this run's quota
      (see Per-run application quota above). Stop only for a fit-flag or if the quota is
      reached.
    - **Resume upload (automated since 2026-09-22):** the Easy Apply modal is now reachable
      via `find`. Before clicking "Upload resume", patch `HTMLInputElement.prototype.click`
      in the page (via `javascript_tool`) so a `type=file` input's `.click()` just attaches
      the input to the DOM instead of opening the native OS picker. Then click "Upload
      resume", `find` the `input type=file`, and call `file_upload` with
      `cv/tailored/<company_slug>/Oleh_Levchenko_CV.pdf`. LinkedIn shows "Resume uploaded
      successfully" and auto-selects the new file (top of the list, today's date) — verify
      that before Next. Re-apply the patch after every page navigation. Fallback if this
      breaks: ask Oleh to click "Upload resume" and pick the file himself.
    - Uncheck "Follow <company>" on the review step (it's a styled DIV — click it by
      coordinate and zoom to verify; `form_input` fails on it). When answering Yes/No
      screening questions, click radios by `find` ref, not coordinates — "This field is
      required" messages shift the layout and mis-hit adjacent radios.
6. Immediately after each submitted application, add a row to `Job Tracker` (use
   `tracker/tracker_io.py`'s `append_job_tracker_row`, see Implementation notes): Company,
   Job Title, Source, Link, Location/Format, Salary, Status=Applied, Date Applied,
   Recruiter/Contact if shown, Next Step, Notes, and **CV Used** =
   `cv/tailored/<company_slug>/Oleh_Levchenko_CV.pdf` (step 5 guarantees this path exists
   either way — tailored or a snapshotted fallback). Don't create an `interviews/<company>/`
   folder yet — that only happens later via `update`, once there's an actual response.
7. At the end of the run (quota reached or postings exhausted), report a summary: how many
   submitted, how many skipped as dedup matches, how many skipped/flagged for fit, and how
   many quota slots remain unused if postings ran out early.

**Cover letter template** (adjust `{role}` / `{company}`):

> I'm a Full Stack Developer with 7+ years of experience across JavaScript/TypeScript,
> Node.js, React, and AWS, currently at The AA. I'm excited about the {role} role at
> {company} and believe my full-stack background and cloud experience would let me
> contribute quickly. I'd welcome the chance to discuss how I can help the team.

### `lead <company>`

Inbound recruiter/hiring-manager message, not sourced from LinkedIn search:

1. Add a `Job Tracker` row: Source notes it's inbound and who reached out; `Date Applied` is
   repurposed as the first-contact date.
2. Don't create `interviews/<company_slug>/` yet — only create it once things reach a
   scheduled call or interview stage (see `fanvue/`, `radioplayer/` for the convention).
3. Confirm with Oleh before writing the row (see Per-run application quota above — `lead`
   isn't covered by a `search` quota, so it always gets a quick confirmation).

### `tailor <company>`

Generates a per-posting CV. Treat the CV as an ad: attention drops with every line, so the
most relevant, most compelling material for this specific posting has to lead — not just be
present somewhere in the document.

1. Gather the posting's requirements (from the job description text, or ask Oleh to paste
   it).
2. Read `cv/base/resume_master.md` in full — including the extended bullet pool — and select,
   reorder, and trim into a CV shaped for this posting: which bullets to keep per role,
   whether the extended pool has a better match than what's currently in the canonical CV,
   and whether the summary line should open with something more relevant to this posting
   than the canonical one does.
3. Write the selection as `cv/tailored/<company_slug>/content.js`, matching the shape of
   `canonicalContent` in `cv/v2/build_cv.js`:
   `module.exports = { name, title, location, contact, summary, coreSkills, experience,
   projects, education }`. Before moving on, diff the `contact` field against
   `cv/base/resume_master.md`'s Contact block (email, phone, LinkedIn, GitHub) — a stale
   copy-paste here has drifted silently before.
4. Run `node cv/tailored/generate.js <company_slug>` to render
   `cv/tailored/<company_slug>/Oleh_Levchenko_CV.docx` via the shared generator, then convert
   to PDF headlessly:
   `soffice --headless --convert-to pdf --outdir cv/tailored/<company_slug>/ cv/tailored/<company_slug>/Oleh_Levchenko_CV.docx`
   (LibreOffice, installed via `brew install --cask libreoffice` — see Implementation notes).
5. Tell Oleh what changed vs the canonical CV (reordered/swapped bullets, summary changes) so
   it can be sanity-checked before the PDF is attached to an application. Oleh still reviews
   and approves the generated PDF before it's used — the headless conversion only removes the
   manual export step, not the review step.

### `update <company>`

Once a response or interview arrives for a company already in the tracker:

1. Create `interviews/<company_slug>/README.md` if it doesn't exist yet (role, recruiter,
   status, round-by-round table, "Next step"), or update the existing one.
2. File round materials per the existing convention: `reflection.md` in English, optional
   `reflection_ua.md`, `transcript.txt` / `interview.wav` if available, empty rounds get a
   `.gitkeep`.
3. Update the top-level `README.md`'s "where I left off" and "next step" (one concrete next
   step, not a list).
4. Confirm with Oleh before writing (see Per-run application quota above — `update` isn't
   covered by a `search` quota, so it always gets a quick confirmation).

## Implementation notes

- PDF export for both `cv/v2` and `cv/tailored/<slug>` uses LibreOffice headless conversion
  (`soffice --headless --convert-to pdf`). Installed via `brew install --cask libreoffice`.
  Word/Pages still work manually if LibreOffice's rendering ever looks off for a given CV.
- Read/append `Job_Search_Tracker.xlsx`'s Job Tracker sheet via `tracker/tracker_io.py`
  (`read_job_tracker()`, `append_job_tracker_row()`) rather than hand-rolling XML parsing —
  it's stdlib-only (`zipfile` + `xml.etree.ElementTree`), no `openpyxl`/`pip install` needed
  (the machine's Python is externally-managed per PEP 668, so ad hoc `pip install` fails
  without `--break-system-packages`).
- `Job_Search_Tracker.xlsx` has no formulas in any sheet, so appending a row is safe without
  a recalculation step — but always read the sheet first so a manual edit isn't clobbered.
- Easy Apply resume upload: automated via the `HTMLInputElement.prototype.click` patch +
  `file_upload` (see `search` step 5), confirmed working 2026-09-22 across 10 applications.
- JD rendering on `/jobs/view/<id>` is flaky ("About the job" often never loads). Read JDs
  instead via the Voyager API from a logged-in LinkedIn tab:
  `fetch('/voyager/api/jobs/jobPostings/<id>', {headers: {'csrf-token': <JSESSIONID cookie
  value>, accept: 'application/json'}})` → `.description.text`, `.title`,
  `.formattedLocation`. Tool output from `javascript_tool` is truncated, so write the
  combined text into the page body and read it with `get_page_text`. `localStorage` is
  blocked by LinkedIn; `window.name` persists across navigations in the same tab.
- JD descriptions can omit the real stack/salary — Easy Apply screening questions or the job
  header sometimes reveal it (e.g. Python/FastAPI questions, a salary chip below the floor).
  Re-check the header salary chip on the job page before starting the apply flow.
- LinkedIn search filters are pre-configured on the account; don't change them.
- The `Recruitment Agencies` sheet exists but is out of scope for this skill unless Oleh
  asks about it directly.
- Ask before creating any new account on an external ATS/job site.
- Per the project's root `CLAUDE.md`: every project `README.md` needs frontmatter
  (`status`, `category`, `stack`) and exactly one next step — don't turn "next step" into a
  list when updating it.
